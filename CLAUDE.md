# CLAUDE.md

The Zadrya substance dataset and the Python pipeline that builds, validates and signs it. The specification is `Application/docs/SPEC.md`, section "Substance dataset".

## Commands

- `make setup`: install the git hooks (lefthook), once per clone.
- `make check`: lint, license metadata and tests. Run before every commit.
- `make ci`: everything CI runs, including authorship and commitlint. Run before opening a pull request.
- `uv run zadrya-data --help`: the pipeline command line. Python 3.12 and all dependencies are managed by `uv` (`uv sync`); never use a global `pip` or `python`.
- `uv run zadrya-data fetch --output <dir>`: download a raw snapshot (`graphql.json`, `mediawiki.json`, `snapshot.json`) from the PsychonautWiki API and wiki (nine requests today, one per second); every other build command reads a snapshot offline with `load_snapshot`. The directory is replaced as a whole and only when the new snapshot is complete, and a directory that holds anything else is refused.
- `uv run zadrya-data diff <old.json> <new.json> [--output report.md]`: the readable diff report of a dataset change (`docs/adr/0007-diff-report.md`); `--old-format base` takes `sources/base/Substances.json` as the old side, normalized alone. `.github/workflows/dataset-diff.yml` posts it as one sticky comment on every pull request that changes `dataset/substances.json`. After a deliberate change of the report, rewrite the golden file with `uv run python -m tests.test_diff` and review its diff.
- Release commands (`docs/adr/0006-release.md`; the procedure is the `release-dataset` skill): `zadrya-data manifest <substances.json> --min-app-version X.Y.Z --date YYYY-MM-DD --output <manifest.json>` (no default date: nothing reads the clock), `zadrya-data sign <substances.json> --output <substances.json.sig>` (key path from `ZADRYA_SIGNING_KEY_FILE`; writes nothing unless a key in `keys/` verifies the signature), `zadrya-data verify <dir>` and `zadrya-data verify --release <dataset-vX.Y.Z|latest>`. All take `--dataset-version` to refuse another version; exit codes are 0 accepted, 1 refused, 2 unreadable or not downloaded.
- **Network.** Exactly two code paths use it, both through `PoliteClient`: `fetch` (the PsychonautWiki API and wiki) and `verify --release` (public assets of a `Zadrya/Data` release on `github.com`, with one redirect allowed and only to `release-assets.githubusercontent.com` or `objects.githubusercontent.com`). Adding a third needs an ADR.
- `uv run pytest tests/test_cli.py`: run one test file. `uv run black .` formats, `uv run mypy` type-checks (strict).

Local tools (Homebrew): `uv`, `lefthook actionlint yamllint markdownlint-cli2 zizmor reuse shellcheck`, plus Node for commitlint.

## Rules

- **Authorship.** Sklyvan is the only author and committer. Never add `Co-Authored-By`, `Claude-Session:` or "Generated with Claude Code" to commits, pull requests or code. The `commit-msg` hook and the `authorship` CI check reject them.
- **Small commits.** One logical change per commit, conventional commit messages, refactors separate from features.
- **Branches.** `feature/<description>` or `fix/<description>`, one pull request per slice (ideally under 400 lines of diff), rebase merge once CI is green and the `reviewer` agent approves. Never push to `main`.
- **Language.** Everything is in English. Use commas, colons or parentheses instead of the em dash (`make lint` fails on U+2014).
- **Secrets.** Only in environment variables or GitHub Secrets, never in the repository, the chat or logs.
- **Licenses.** Original code carries the SPDX header `GPL-3.0-or-later`. Files without a comment syntax are covered by `REUSE.toml`.
- **Signing key.** The private Ed25519 key is never generated, read or handled by Claude. Signing reads its path from the environment variable `ZADRYA_SIGNING_KEY_FILE` (and the password of an encrypted key from `ZADRYA_SIGNING_KEY_PASSWORD`), and CI uses the `DATASET_SIGNING_KEY` secret. No private key is ever committed, not even a test key.
- **No release without review.** Every dataset change is opened as a pull request with a readable diff, and only Sklyvan approves a release.

## Gotchas

- Tests never touch the network and must keep coverage at 90 % or higher (`pyproject.toml`). Network code is tested with `httpx.MockTransport` replaying the recorded answers in `tests/fixtures/api/` (`tests/api_fixtures.py`). All requests go through `PoliteClient` (`src/zadrya_data/http.py`): never create another `httpx` client.
- No real snapshot is committed yet (it lands with the first dataset). Write one outside the repository when you need real data.
- A snapshot is tied to the code that fetched it: `load_snapshot` rejects one whose query, endpoints, hashes or counts do not match (`docs/adr/0002-extraction-and-raw-snapshot.md`). After changing `QUERY` in `graphql.py`, fetch again.
- Normalization (`src/zadrya_data/normalize/`, rules in `docs/adr/0004-normalization.md` and, for tolerance, cross tolerance and interactions, `0005-relations.md`) is pure and never silent: every drop, fallback or repair goes into the report, and a new rule needs a reference case in `tests/fixtures/normalize/` (small JSON files maintained by hand; `tests/normalize_cases.py` fills in the keys a case leaves out). Six tables there are the owner's to confirm, not ours to extend quietly: `ALLOWED_API_ONLY` (which API-only substances enter the catalog), `CLASS_TO_CATEGORY`, `QUALIFIED_UNITS` (base units such as `mg THC` that replace a plain API unit), `TOKEN_TO_GROUP` (cross tolerance tokens), `NAME_TO_GROUP` and `GROUPS` (interaction class names and the rule that picks each group's members). Interaction groups are never expanded into substance pairs: the app resolves them through `members` in both directions (ADR 5). Normalization raises if a dose ever loses an upper boundary the base file has: fix the rule, never the guard. The API `summary` is never used: it is the first text of the wiki page, often a banner.
- `uv.lock` is committed and CI installs with `--locked`: after changing dependencies run `uv lock` and commit the lock file in the same commit.
- The schemas in `schema/` are the only copy: `src/zadrya_data/schemas/` holds symbolic links to them, which the build resolves into the wheel. A new schema file needs its link.
- Schema fixtures are generated: edit `tests/schema_cases.py`, run `uv run python -m tests.schema_cases` and commit the files. A mutation test (`tests/test_schema_mutations.py`, about 10 seconds) fails when removing one constraint of a schema changes no fixture result, so a new rule needs a fixture that breaks it. Python and Dart read regular expressions differently: end every pattern with `$(?![\s\S])` and avoid `\s` (`schema/README.md`).
- Data derived from PsychonautWiki is CC BY-SA 4.0 (text) and CC BY 4.0 (semantic data), while code is GPL-3.0-or-later. Keep `REUSE.toml` accurate when data files are added.
- Actions must be pinned by full commit SHA: the organization enforces it and unpinned workflows do not start.
- The shared scripts in `scripts/` and the base workflows are duplicated in all four Zadrya repositories on purpose, so that each repository can run `make ci` on its own. When you change one, change it in all four.
- The `authorship` and `commitlint` checks run the scripts from the pull request head, so a pull request that edits `scripts/check-*.sh`, the `Makefile` or those workflows validates itself: review such diffs with extra care.
- Tool versions are pinned in `scripts/install-ci-tools.sh` and the `Makefile`, and Dependabot does not track them: bump them by hand. The same goes for uv: its version and checksum in `.github/workflows/ci.yml` (twice) and the `uv_build` range in `pyproject.toml`.
- Dependency review (license allowlist in `.github/workflows/licenses.yml`) only runs in CI, so `make ci` cannot tell you that a new dependency has a license outside the list.
- Dependabot pull requests fail the `authorship` check by design: re-commit the bump as Sklyvan on a branch and close the Dependabot pull request (see `Application/docs/adr/0002-dependabot-and-authorship.md`).
- Tests and scripts that create a git repository must first clear the variables git exports to hooks (`unset $(git rev-parse --local-env-vars)`): git exports `GIT_INDEX_FILE` to every pre-commit hook, and in a linked worktree or a submodule it also exports `GIT_DIR`, which makes every git command act on the real repository. `scripts/test-hooks-isolation.sh` guards the hook tests against this.
- Signing lives in three library modules (`docs/adr/0003-dataset-signature.md`): `signing.py` (Ed25519, the strict `substances.json.sig` format, key loading), `manifest.py` (build, deterministic bytes, checks) and `release_check.py` (`verify_release`, the full acceptance check in the order the app uses: signature, hash, schemas, consistency). Commands and workflows must call these and never reimplement a step. Every refusal derives from `zadrya_data.errors.ReleaseRejectedError`. `VerifiedRelease.unsigned_min_app_version` comes from the unsigned manifest: it may refuse a release, never accept one. Whether the manifest gets its own signature is a pending owner decision recorded in the ADR.
- `.github/workflows/release.yml` signs the committed `dataset/substances.json` of `main` and never rebuilds it. Only the owner starts it and approves its `sign` job (environment `release`, the only job that can read `DATASET_SIGNING_KEY`): never run it yourself. Keep that job free of caches, debug output and extra permissions.
- Dataset releases are tagged `dataset-vX.Y.Z` with the `datasetVersion` inside the signed bytes, never `vX.Y.Z` (that is the app's tag scheme). `verify --release` rejects a release whose tag and signed version differ.
- Pinned public keys live in `keys/` (`keys/README.md`): one canonical PEM per key, at most two. With no key there (the state until the owner provides one), every verification fails with `NoPinnedKeysError`, on purpose.
- Tests create their own throwaway keys in memory with `cryptography` (`Ed25519PrivateKey.generate()`), and write them only under `tmp_path`. `tests/test_no_private_keys.py` fails when a tracked or new file, or the staged content of the index, contains the header of a PEM private key, so never spell that header out in code or documentation. The committed vectors in `tests/test_signing.py` are public material only.
- Errors about the private key never include its content, the password or the value of `ZADRYA_SIGNING_KEY_FILE`. `load_private_key` reads and parses in a helper that returns a reason, so the error has no cause, no context and no frame holding the key: keep it that way. This limits what a traceback shows; it does not protect against a debugger or a memory dump. The key file must have mode 0600 or stricter and hold exactly one PKCS#8 PEM.
- Before every push: `git log --format='%an <%ae>%n%B' origin/main..HEAD`.
- `sources/` holds vendored inputs: stored byte for byte, pinned by hash in a test (`tests/test_base_file.py`) and never edited. Every new external input needs its source address, commit and license in `NOTICE` and `DATA_LICENSES.md`, and its annotation in `REUSE.toml`, in the same pull request.
