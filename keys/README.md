# Pinned public keys

This directory holds the Ed25519 **public** keys that dataset signatures are accepted from, and nothing else. The pipeline reads them with `zadrya_data.signing.load_public_keys`, and the app pins the same keys in its code. The decisions behind the format are in [`docs/adr/0003-dataset-signature.md`](../docs/adr/0003-dataset-signature.md).

There is no key here yet: the owner has not published the first one. Until then verification fails with "no pinned public keys", which is the intended behavior. It never passes without a key.

## What lives here

- One file per key, named `<name>.pem`. The name (without `.pem`) is what verification reports as the key that matched, so make it say something, for example `2026-11.pem`.
- At most two files: the current key and, during a rotation, the next one. Files are read in the order of their names.
- Each file is exactly one public key as PEM (SubjectPublicKeyInfo): the `BEGIN PUBLIC KEY` line, one line of base64 and the `END PUBLIC KEY` line, with line feeds. Comments, blank lines, carriage returns, a second key in the same file, a key of another type and the same key under two names are all rejected.
- This `README.md`. Files that do not end in `.pem` are ignored by the loader.

## No private key, ever

The private key is generated by the owner on their own machine and lives outside every repository (a password manager, and the `DATASET_SIGNING_KEY` secret of the `release` environment for signing in CI). It is never committed here, not even encrypted, and not even a test key: tests create their own throwaway keys in memory. A test (`tests/test_no_private_keys.py`) fails if any file of the repository contains the header of a PEM private key, and the loader refuses a private key placed in this directory.

Signing reads the private key from the file named by the environment variable `ZADRYA_SIGNING_KEY_FILE`.

## The form the app pins

The app pins the raw 32 bytes of each public key, not the PEM. Both forms come from the same file:

```sh
uv run python -c "
from pathlib import Path
from zadrya_data.signing import load_public_keys
for key in load_public_keys(Path('keys')):
    print(key.name, key.base64, key.raw.hex())
"
```

## Rotation

A release is accepted when its signature verifies with any one of the pinned keys, so a rotation never leaves an installed app without a key it trusts, as long as the steps are taken in this order:

1. **Add the new key.** The owner generates a new key pair and sends only the public key. Add it here as a second `.pem` file, next to the current one.
2. **Ship an app that pins both.** Release an app version that pins the current and the new key, and wait until the versions that pin only the old key are no longer supported. Releases are still signed with the old key during this time.
3. **Start signing with the new key.** Apps that pin both accept it. If older apps must be kept out, raise `minAppVersion` in the manifest of that release.
4. **Remove the old key.** Delete its file here, and drop it from the app in a later version. From then on a release signed with the old key is rejected.

If a private key is lost or exposed, skip the waiting: add the new key, ship an app that pins only the new one, and remove the old key at once. Apps that still pin only the old key keep the dataset they have and can no longer be updated, which is the safe outcome.
