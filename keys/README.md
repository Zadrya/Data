# Pinned public keys

This directory holds the Ed25519 **public** keys that dataset signatures are accepted from, and nothing else. The pipeline reads them with `zadrya_data.signing.load_public_keys`, and the app pins the same keys in its code. The decisions behind the format are in [`docs/adr/0003-dataset-signature.md`](../docs/adr/0003-dataset-signature.md).

There is no key here yet: the owner has not published the first one. Until then verification fails with "no pinned public keys", which is the intended behavior. It never passes without a key.

## What lives here

- One file per key, named `<name>.pem`. The name (without `.pem`) is what verification reports as the key that matched, so make it say something, for example `2026-11.pem`.
- At most two files: the current key and, during a rotation, the next one. Files are read in the order of their names.
- Each file is exactly one public key as PEM (SubjectPublicKeyInfo): the `BEGIN PUBLIC KEY` line, one line of base64 and the `END PUBLIC KEY` line, with line feeds. Comments, blank lines, carriage returns, a second key in the same file, a key of another type and the same key under two names are all rejected, and so are the eight points of small order (encodings that are not real keys and for which signatures can be forged).
- This `README.md`. Files that do not end in `.pem` are ignored by the loader.

## No private key, ever

The private key is generated by the owner on their own machine, encrypted with a passphrase, and lives outside every repository (a password manager, and, decrypted, the `DATASET_SIGNING_KEY` secret of the `release` environment for signing in CI). It is never committed here, not even encrypted, and not even a test key: tests create their own throwaway keys in memory. A test (`tests/test_no_private_keys.py`) fails if any file of the repository contains the header of a PEM private key, and the loader refuses a private key placed in this directory.

Signing reads the private key from the file named by the environment variable `ZADRYA_SIGNING_KEY_FILE`. The variable holds the path, never the key. The file must hold exactly one key and be accessible to its owner only (mode 0600 or stricter), or it is refused.

## Generating a key pair (owner only)

The owner runs this on their own machine. The `openssl` that macOS ships is LibreSSL 3.3.6, which cannot create or read Ed25519 keys, so the commands use OpenSSL 3 from Homebrew. Replace `<encrypted.pem>` with a file outside every repository (the `release-dataset` skill uses the same name).

```sh
brew install openssl@3
umask 077
"$(brew --prefix openssl@3)/bin/openssl" genpkey -algorithm ed25519 -aes256 -out <encrypted.pem>
"$(brew --prefix openssl@3)/bin/openssl" pkey -in <encrypted.pem> -pubout
```

The first command asks twice for a new passphrase and writes the private key **encrypted** with it (PKCS#8, AES-256), so the file is never on disk in plain text. `umask 077` makes it readable by its owner only. The second command asks for the passphrase once and prints the public key, three lines that start with `BEGIN PUBLIC KEY`: that output, and nothing else, is what goes into this directory as `<name>.pem` and what is shared.

Keep the encrypted file and its passphrase in the password manager. Signing locally reads the encrypted file directly, with the passphrase in `ZADRYA_SIGNING_KEY_PASSWORD`. For CI, the decrypted key goes into the `DATASET_SIGNING_KEY` secret of the `release` environment straight from a pipe, never through a plain file or the clipboard; the exact commands for both are in the `release-dataset` skill.

The private key, encrypted or not, never enters a repository, a chat, an issue, a pull request or a log, in whole or in part. If it was ever pasted anywhere else, treat it as exposed and rotate.

## The form the app pins

The app pins the raw 32 bytes of each public key, not the PEM. Both forms come from the same file:

```sh
uv run python -c "
from pathlib import Path
from zadrya_data.signing import load_public_keys
for key in load_public_keys(Path('keys')):
    print(key.name, key.base64, key.raw.hex())
"
```

## Rotation

A release is accepted when its signature verifies with any one of the pinned keys, so a rotation never leaves an installed app without a key it trusts, as long as the steps are taken in this order:

1. **Add the new key.** The owner generates a new key pair and sends only the public key. Add it here as a second `.pem` file, next to the current one.
2. **Ship an app that pins both.** Release an app version that pins the current and the new key, and wait until the versions that pin only the old key are no longer supported. Releases are still signed with the old key during this time.
3. **Start signing with the new key.** Apps that pin both accept it. If older apps must be kept out, raise `minAppVersion` in the manifest of that release.
4. **Remove the old key.** Delete its file here, and drop it from the app in a later version. From then on a release signed with the old key is rejected.

### When a key is lost

A lost key (destroyed, with no sign that anyone else has it) cannot sign anymore, and nobody can forge with it. Add the new key, ship an app that pins it, and remove the old key. Apps that pin only the old key keep the dataset they have and can no longer be updated: inconvenient, and safe.

### When a key is exposed

An exposed key is not a safe state. Until an app stops pinning it, anyone who holds the key and also controls what the app downloads (the release assets, the account that publishes them, or the connection) can make that app accept a dataset of their own. Removing the key from this directory does not change that: only an app update does, and only for the users who install it.

1. Stop signing with the exposed key at once.
2. Add a new key here, and release an app version that pins only keys that are not exposed. That release is the fix, so it should not wait for the usual rotation period.
3. Remove the exposed key here in the same change, so the pipeline rejects anything signed with it.
4. Tell users, in the release notes and on the site, that older app versions should not download dataset updates. Their bundled dataset stays trustworthy, because it is part of the signed app and not of the download.

There is no revocation list and no way to reach an installed app other than an update. That limit is recorded in `docs/adr/0003-dataset-signature.md`.
